# 阶段 3 报告：PushCube-v1 上的 PPO

> 日期：2026-11-02
> 对应《具身智能实验与实践学习计划（修订版）》第 5 节
> 代码：本目录 `run.py`、`evaluate.py`；baseline：`third_party/ManiSkill@a4a4f92`（v3.0.1）

---

## 1. 研究问题与预期

**问题**：在 ManiSkill 的 `PushCube-v1` 上，用官方 PPO baseline 能否训出一个可用的推方块策略？
训练—保存—独立评估—视频这条链路在 GPU 仿真下能否稳定复现？

**成功判定**：`info["success"]` 为当步口径；报告「成功数/回合数」，而不是只看平均回报。
**预算**：200 万 timesteps、2048 并行环境、8 GB 显存；实际耗时 241 秒。

## 3. 数据与方法

### 3.1 任务接口（已由阶段 2 核对）

| 项 | PushCube-v1 |
|---|---|
| 观测 | state，扁平 35 维 = qpos(9) + qvel(9) + tcp_pose(7) + goal_pos(3) + obj_pose(7) |
| 动作 | 8 维：panda 7 关节位置增量 + 1 夹爪，`Box(-1,1)` |
| 控制模式 | `pd_joint_delta_pos` |
| 奖励 | `normalized_dense`：每步是势函数变化，不是「存活 +1」 |
| 成功 | 方块中心距目标中心 **< 0.1 m** 且仍在桌面；当步判定，成功时 `terminated=True` |
| 成功的「松紧」 | **扫过即算**：不要求停留、不要求速度为零、无朝向要求 |
| 随机化 | 方块 xy 在 20 cm × 20 cm 内均匀；目标恒为 `方块 + [0.2, 0]`，推距恒定 20 cm |
| episode 上限 | 50 步（`truncated=True`） |

### 3.2 训练配置

| 超参 | smoke | train |
|---|---|---|
| `num_envs` | 64 | **2048** |
| `total_timesteps` | 51,200 | **2,000,000** |
| `num_steps` | 50 | 20 |
| `num_minibatches` / `update_epochs` | 8 / 4 | 32 / 8 |
| `gamma` / `gae_lambda` | 0.8 / 0.9 | 0.8 / 0.9 |
| `eval_freq` | 5 | 10 |
| 实际耗时 | 33.8 秒 | **241.0 秒** |
| 实测吞吐 | ~1,930 步/秒 | **8,786–9,217 步/秒** |

`gamma=0.8`、`num_steps=20` 都是官方 README 的 PushCube 示例值，**不是**常见的 0.99 / 128，沿用是为了不引入未经验证的偏离。

吞吐低于阶段 2 测得的纯物理 68,000 步/秒，差异来自 PPO 更新本身：每次迭代要跑
`40960 batch × 8 epochs ÷ 32 minibatches = 256` 次梯度更新。

### 3.3 评估协议

- **训练内评估**：官方 baseline 每 10 次迭代评估一次，8 个环境 × 50 步 → 每次约 8 个回合
- **独立评估**：`evaluate.py` 加载 `final_ckpt.pt`，20 回合，种子 100–119，`deterministic=True`，
  每个回合从独立 `reset(seed=...)` 开始
- 官方 `--evaluate` 被放弃，因为它用训练种子重置评估环境，不满足种子分离

## 5. 分析

### 5.1 **返回值在这类任务上是反向指标**

| 回合类型 | mean_return | return 范围 | steps | 结束原因 |
|---|---|---|---|---|
| 成功的 19 个 | **4.42** | 3.81 – 4.89 | 10–19 | `terminated` |
| 失败的 1 个（seed 113） | **23.40** | 23.40 | 50 | `truncated` |

失败的回合 return 是成功回合的 **5.3 倍**。原因是 `normalized_dense` 奖励是势函数变化，
成功会提前终止 episode，而失败的策略熬满 50 步能持续累积小幅奖励。

**结论：在这个任务上按 return 排序会选出最差的策略。** 这与 W7 里「训练回报上升但任务成功率降到 0%」
是同一类问题——**奖励上升不等于任务完成**，必须以 `success` 为准。

### 5.2 小样本评估的噪声比训练波动更大

训练内评估从 iter 31 的 1.000 掉到 iter 41 的 0.625，看起来像「训练后期退化」；
但同一个 `final_ckpt` 用 20 回合独立评估是 95%。

三次评估的样本量分别是 8 / 8 / 20 回合，**8 个回合里差 3 个就是 0.375 的跳变**。
所以那个 0.625 更可能是抽样噪声，而不是策略真的崩了。这也说明计划书为什么要求
正式消融每个模型至少 50 回合：20 回合时 19/20 的 95% Wilson 置信区间就有 **[76%, 99%]** 这么宽。

### 5.3 `terminated` 与 `success` 在本任务高度重合，但别当通用规律

19 个成功回合全部是 `terminated=True`，唯一失败的是 `truncated=True`。
这是因为 PushCube 的实现里「成功即终止 episode」。换成成功不终止的任务（如持续控制类），
这个对应关系就完全不成立。**报告里应各自统计，不要互相替代。**

### 5.4 这不是「复现官方成功率」

官方 README 对 PushCube 只说明「最快的任务之一，GPU 上不到 1 分钟」，**没有给出具体成功率数字**。
所以本文报告的 95% 属于「在官方 baseline 上完成了自己的训练与独立评估」，
**不能表述为「复现了官方的 XX%」**。这是计划书反复强调的三种结论区分。

## 6. 局限

1. **单一训练种子**（seed 1）。要谈稳定性至少需要 3 个训练种子。
2. **评估 20 回合**，置信区间宽（[76%, 99%]），且全部成功/失败集中在少数初始条件上。
3. **训练内评估只有 8 回合/次**，曲线上的抖动无法区分噪声与真实退化。
4. **只做了 PushCube**，未涉及更难的 PickCube（抓取）。
5. **未做参数扫描**：`num_envs`、`num_steps`、`gamma` 都是照官方示例，没有验证其在本机是否最优。
6. **成功判据本身偏松**：10 cm 容差是方块边长（4 cm）的 2.5 倍，目标圈直径是方块边长的 5 倍，
   且「扫过即成功」（当步判定 + 成功即终止）。所以 95% 主要说明策略学会了
   「绕到方块后方并沿 +x 推」，**不代表精细定位、位姿对齐或抓取能力**。
   若后续要做方法间消融，应收紧 `goal_radius` 或要求连续 N 步保持 success，否则区分力不足。
