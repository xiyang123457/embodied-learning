# 阶段 4 报告（进行中）：ACT 在 Transfer Cube 上的首个闭环

> 日期：2026-11-03
> 对应《具身智能实验与实践学习计划（修订版）》第 6 节
> ACT 官方仓库 commit `742c753`；环境 `.venv-act`

**状态：链路已打通，结果为短训练（200 epochs），不是最终基线。**

---

## 1. 研究问题

**问题**：从同任务示范数据出发，能否完成「示范生成 → 原生图像策略训练 → checkpoint 重载 →
在同一仿真任务上独立 rollout 评估」这条闭环？这一步验证的是**接口与流程**，
不是追求成功率。

**判定**：计划书要求「报告成功数/总数及失败原因」，并明确 **loss 下降不等于任务成功**。

## 4. 训练

| 项 | 值 |
|---|---|
| 数据 | 25 条（20 训练 / 5 验证） |
| `batch_size` / `chunk_size` / `hidden_dim` | 4 / 100 / 512 |
| `kl_weight` / `dim_feedforward` / `lr` | 10 / 3200 / 1e-5 |
| 参数总量 | **83.92 M** |
| epochs | 200 |
| 总耗时 | **452.75 秒**（约 2.26 秒/epoch） |
| 最优 | epoch 164，val loss **0.246** |

loss 轨迹：val 从 55.4 降到 0.25–0.42，train 稳定在 2.1–2.4（l1 ≈ 0.5）。

**为什么 200 个 epoch 只用了 7.5 分钟**：ACT 的 `EpisodicDataset` 按 **episode** 采样，
每 epoch 只有 `ceil(20 / batch_size)` = **5 个 batch**。所以 200 epochs 只对应约 1000 次梯度更新，
官方默认的 2000 epochs 也只有约 10000 次。这不是"训练很快就够了"，而是这个训练器的更新次数天然很少。

## 5. 评估（50 次 rollout，`policy_best.ckpt`，`--temporal_agg`）

| 指标 | 值 |
|---|---|
| **成功率** | **26%（13/50）** |
| 平均 return | 164.32 |

奖励分档（任务奖励 0–4，对应 触及 → 举起 → 尝试交接 → 完成交接）：

| 档位 | 含义 | 达成 |
|---|---|---|
| ≥ 1 | 夹爪碰到方块 | 23/50（**46%**） |
| ≥ 2 | 举起且未落桌 | 21/50（**42%**） |
| ≥ 3 | 尝试与另一只手交接 | 13/50（**26%**） |
| ≥ 4 | 成功交接 | 13/50（**26%**） |

代表案例：`runs/train25_e200/clips/success_rollout8.mp4`、`failure_rollout0.mp4`。

---

## 6. 分析

### 6.1 瓶颈在「举起之后」，不是「够到方块」

分档数据把失败切得很清楚：

- 46% 能碰到方块，42% 能举起来 —— 前两个阶段基本打通
- 从 **42% 掉到 26%** —— 真正的损失发生在「举着方块交给另一只手」这一段

失败的 37 个回合里，大部分卡在"举起来了但没完成交接"，而不是"根本没找到方块"。
这与任务设计一致：双臂交接需要两只手在时间与空间上配合，是这条任务里最难的一环。

### 6.2 val loss 0.25 与成功率 26% 并不矛盾

验证 loss 降到了 0.25（l1 ≈ 0.5），但成功率只有 26%。这正是计划书提醒的情况：
**loss 衡量的是动作序列的 L1 误差，不是任务是否完成。**

抓到方块之后有没有完成交接，取决于长时间闭环中的累积误差——单步动作"接近"正确，
闭环里仍会漂移。所以本阶段的所有结论都以 rollout 成功率为准。

### 6.3 这不是 ACT 的方法上限

当前只训练了 **200 / 2000 epochs**（1/10），数据 **25 / 50 条**（1/2）。
26% 是**短训练 + 少数据**的结果，不能据此判断 ACT 在该任务上的能力。

---

## 7. 局限

1. **训练量远低于官方**：200 vs 2000 epochs，且每 epoch 仅 5 次更新。
2. **数据只有 25 条**，受内存限制，非计划书建议的 50 条。
3. **单训练种子**（seed 0）。
4. **评估不能指定种子**：`num_rollouts = 50` 硬编码，且不使用独立种子列表，
   因此无法像阶段 3 那样做「训练/评估种子分离」的严格对照。
5. 未做 `--temporal_agg` 的消融（本次已开启）。

---

## 8. 下一步

1. **跑满 2000 epochs**（约 75 分钟），用同一份 25 条数据，观察成功率是否继续上升。
   这是判断「26% 是训练不足还是方法瓶颈」最直接的一步。
2. **若提升明显**，再考虑解决内存约束以便用 50 条数据：
   裁剪成功后的冗余帧（实际成功只需 100–200 步，数据存了 400 步），预计可省一半内存。
3. **若跑满后仍停在低位**，再分析失败回合的交接阶段轨迹，而不是继续加 epochs。
