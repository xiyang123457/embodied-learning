## 1. 研究问题与预期

**问题**：在一个已知可解、算力需求极低的经典控制任务上，PPO 能否从完全随机的策略出发，
学到稳定的闭环控制？整条「训练 → 保存 → 独立评估 → 视频 → 曲线」的管线能否跑通？

**成功判定**：`CartPole-v1` 的官方"解决"标准是连续 100 回合平均回报 ≥ 475（单回合上限 500）。
本阶段目标不是刷分，而是验证管线与记录规范，门槛设为「20 个独立评估回合 + 重载 checkpoint 后结果一致」。

**预算**：100k 训练步、单卡 CPU、评估 20 回合。实际训练耗时 339.8 秒。

## 3. 数据与方法

### 3.1 任务接口（先看清接口再谈算法）

| 项 | CartPole-v1 |
|---|---|
| 观测 | `Box(4,)`，4 维连续：小车位置 x (m)、小车速度 v (m/s)、杆角度 θ (rad)、杆角速度 ω (rad/s) |
| 动作 | `Discrete(2)`：0 = 向左推，1 = 向右推（固定力，不是力矩） |
| 奖励 | 每存活一步 +1，无其他分量 |
| `terminated` | 杆倾角超阈值或小车出界 → 真实终止 |
| `truncated` | 达到 500 步上限 → 时间截断 |

**这个区分很重要**：CartPole 的失败全部来自 `terminated`，`truncated` 只在"活满 500 步"时触发。
所以本任务的回报等价于"存活步数"，不存在 W7 里那种"截断是否该 bootstrap"的歧义。

### 3.2 训练设置

| 超参数 | 值 | 说明 |
|---|---|---|
| 算法 | PPO（`MlpPolicy`） | 网络 `[4 → 64 → 64 → 2]`，约 4.6k 参数 |
| 并行环境 | 4 | |
| `n_steps` / `batch_size` / `n_epochs` | 128 / 256 / 10 | 每轮 512 步 → 2 个 minibatch × 10 epochs |
| `gamma` / `gae_lambda` / `clip_range` | 0.99 / 0.95 / 0.2 | |
| 学习率 / `ent_coef` | 3e-4 / 0.0 | |
| 总步数 | 100,000 | 每轮 512 步 → 约 195 次策略更新 |

### 3.3 评估协议

- 全新环境实例，关闭训练更新，`deterministic=True`
- 种子 100–119，共 20 回合，与训练种子 0 完全分离
- 逐回合记录回报、步数、终止/截断标志（`eval_random.csv`、`eval_ppo.csv`）
- 训练前后各录 1 个回合视频
- **重载验证**：从 `model.zip` 重新加载后再评估同一批种子，要求逐回合结果一致

## 5. 分析

### 5.1 随机策略为什么是 21 而不是 10

随机策略在 CartPole 上平均存活约 20–22 步。这个数字本身就是对环境动力学的校验：
如果随机策略能活 100 步以上，说明 reset 分布或终止条件被改过。

### 5.2 **标准差 0.0 不是"策略稳定"，是指标撞顶了**

20/20 全部等于 500，而 500 是 `max_episode_steps` 的截断上限。**所有回合撞到同一个天花板，
方差自然为 0。** 这不代表策略"每次都完美"，只代表"20 回合内没有一次失败到足以区分"。

这和 W6 的教训是同一类问题：**判据一旦饱和，就没有区分力**。W6 里 5 cm 判据下三种方法
全部 20/20，收紧到 2 mm 才分得开；这里 20 回合全部撞顶，要区分策略强弱只能：
① 加大初始状态扰动（更大的 θ 偏移）、② 提高截断上限、③ 统计"达到 500 之前的步数分布"。

### 5.3 曲线末端滑动平均 421，评估却是 500

滑动平均窗口 20，覆盖的是"最近 20 个训练回合"。训练从 82.7k 步才开始稳定 500，
而 100k 时窗口内仍含有 80k 之前的低分回合，所以均值被拖到 421。
**这不是矛盾，是"训练期指标"与"评估期指标"统计口径不同**——报告时必须两个都给，
不能只挑好看的。

### 5.4 训练曲线的震荡说明什么

40k–80k 之间出现多次"接近 500 → 掉到 60–150"的剧烈震荡。这是 PPO 的典型现象：
`n_epochs` 内的策略更新幅度与 `clip_range=0.2` 共同决定每次更新的步长，早期策略刚开始
利用"保持杆直立"这一模式时，一次过大的更新就会把策略打回差解。稳定收敛前经历了约 3 次
明显的崩塌-恢复。**所以"某次评估 500"不能当作收敛证据，要看连续多回合。**

### 5.5 为什么 PPO 不用 GPU

MlpPolicy 只有约 4.6k 参数，每次前向是 `4×4 @ 4×64` 级别的矩阵乘，而 GPU 单次 kernel
启动开销约 5–20 μs，比计算本身还贵；且 PPO 的瓶颈是 CPU 上的环境采样（100k 步串行）。
SB3 官方也明确提示非 CNN 策略应跑 CPU，否则"GPU 利用率低且可能更慢"。

GPU 的能力已经在阶段 0 单独验收：`torch 2.15.0+cu132`、`capability (12,0)`（sm_120 被正确识别）、
4096×4096 矩阵乘 + 反向传播通过、峰值显存 288 MB。**CartPole 不适合用 GPU，不代表 GPU 不可用。**

脚本保留 `--device cuda` 参数，需要计时对照时可直接跑：

```bash
./.venv-ppo/bin/python scripts/ppo_cartpole.py --timesteps 20000 --device cuda --tag gpu_bench
```

## 6. 局限

1. **任务过于简单**：4 维状态、2 维离散动作，没有任何感知环节。结论**不能外推到**连续控制、
   视觉策略或机械臂任务。
2. **单一训练种子**：只跑了 seed 0。要谈"PPO 在 CartPole 上稳定收敛"，至少需要 3 个训练种子
   （计划书第 7 节对消融的要求）。本阶段是管线验证，不声称统计稳定性。
3. **评估回合数偏少**：20 回合，且全部撞顶，无法估计真实成功率的置信区间。
4. **`reward = 存活步数`**，与任务成功同构，不存在 W7 那种"奖励上升但任务失败"的 reward hacking
   空间。这不代表 PPO 在稀疏奖励任务上也没问题。
