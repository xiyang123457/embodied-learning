# 具身智能实验与实践学习计划（修订版）

> 修订日期：2026-11-02  
> 适用设备：Ubuntu 笔记本、NVIDIA RTX 5060 Laptop（显存以 `nvidia-smi` 实测为准）、32GB 内存、1TB 存储。  
> 起点：已学习强化学习、扩散模型、VLA 及部分世界模型理论；具有 Robocon 深度相机与视觉定位项目经历。  
> 核心目标：从“理解论文中的方法”过渡到“独立完成训练—评估—可视化—误差分析—对照实验”。

## 0. 总原则

- **先闭环，再扩展。** 每阶段先完成最小可交付物，碰到不理解的问题再回补理论。
- **先复现 baseline，再修改。** 不以覆盖所有平台或首次就训练成功为目标。
- **训练、验证和评估分开。** 保存完整配置、随机种子、模型和失败视频；不要只展示最好的一次结果。
- **区分工具角色。** ManiSkill 提供主要基于 SAPIEN 的机器人任务；MuJoCo 是物理引擎；LeRobot 提供数据与策略工具。环境、数据和策略不会自动互通。
- **时间有弹性。** 周次是建议，不是截止日期；课程繁忙时按阶段门槛推进，可以暂停选修而保留主线。
- **真实硬件先匹配再运行。** 仿真成功不等于真机可用；仅在具备相应机械臂、标定、接口和安全条件时开展真机实验。

## 1. 实验路线总览

| 阶段 | 项目与主要工具 | 最小产出 | 优先级 |
|---|---|---|---|
| 0 | 环境检查：驱动、PyTorch、渲染 | GPU 运算与渲染检查、环境记录 | 必做 |
| 1 | 快速 PPO 基础：Gymnasium、Stable-Baselines3 | CartPole 曲线、checkpoint、评估视频 | 必做 |
| 2 | ManiSkill 演示：PushCube / PickCube | 官方演示视频、观测与动作说明 | 必做 |
| 3 | ManiSkill PPO：PushCube → PickCube | checkpoint、成功率、失败视频与报告 | 主线 |
| 4 | ACT 兼容仿真：官方 ACT 仓库及其 Transfer Cube | 示范数据、训练 checkpoint、仿真 rollout | 主线 |
| 5 | ACT 示范数据量消融 | 可复现的对照表和导师汇报 | 主线 |
| 6–8 | Diffusion Policy / MuJoCo / SmolVLA | 条件成熟后选择一项深入 | 选修 |
| 并行 | Robocon 深度相机与视觉定位 | 有测量依据的误差报告 | 可并行 |

**路线选择：**阶段 3 和阶段 4 使用不同仿真任务，不将两者的成功率直接比较。ACT 默认采用 [ACT 官方仓库](https://github.com/tonyzhaozh/act)自带的 `sim_transfer_cube_scripted`，其示范、策略和仿真评估属于同一套流程。LeRobot 是后续可选路线；ManiSkill 与 LeRobot 的对接需单独验证，不是阶段 4 的前置条件。

## 2. 第 0 阶段：搭建与验证环境（建议 1–3 天）

**目标：**确认 GPU 运算和仿真渲染可用，建立可复现环境。

- [ ] 运行 `nvidia-smi`、`free -h`、`df -h`，记录显卡、显存、驱动、内存与剩余磁盘。
- [ ] 按 [PyTorch 官方安装指引](https://pytorch.org/get-started/locally/)选择支持本机 GPU 和驱动的构建；检查 `torch.cuda.is_available()`，在 GPU 上完成一次张量运算及反向传播。可用但运行时报架构错误仍不算通过。
- [ ] 为 PPO 基础、ManiSkill、ACT 分别建虚拟环境。记录操作系统、Python、驱动、PyTorch、CUDA 构建、项目版本或 Git commit，以及安装命令和依赖导出。
- [ ] 按 ManiSkill 当前版本检查渲染、无窗口录制及图形驱动；若训练正常但显示失败，分别排查渲染后端和显示会话。
- [ ] 建立目录：`configs/`、`logs/`、`checkpoints/`、`videos/`、`reports/`；大数据集注明来源及存储位置。

**阶段门槛：**GPU 小脚本可运行；记录实际显存和环境；至少能启动并保存一个仿真画面。渲染暂不可用时先完成阶段 1，并为修复设时限。

**兼容提醒：**RTX 5060 Laptop 较新，旧教程固定的 PyTorch/CUDA 组合不一定支持。ACT 原仓库的历史依赖与新 GPU 所需构建可能冲突；不要为迁就旧版本覆盖已验证的其他环境。LeRobot 文档的 `main` 与稳定版安装要求、命令和数据格式会变化，必须对照所固定版本阅读，不保证直接共享依赖。

## 3. 第 1 阶段：快速 PPO 基础（建议 2–4 天）

**项目：**CartPole-v1；LunarLander 与 DQN 仅在有余力时选做。

- [ ] 先运行随机策略，说明 observation、action、reward、`terminated` 与 `truncated`。
- [ ] 使用 Stable-Baselines3 的 PPO 完成短训练，保存配置、日志与 checkpoint。
- [ ] 在独立环境、未用于训练的种子上评估至少 20 回合，记录平均回报、标准差和回合数；录制训练前后视频。
- [ ] 画回报曲线，用自己的话解释采样、策略更新与评估；选做一个参数变化，明确这只是练习而非正式结论。

**阶段门槛：**能从保存的 checkpoint 重新加载并评估；有曲线、视频和一页说明。若没有达到期望回报，先检查奖励、终止、训练步数及评估模式，记录后可继续阶段 2。

## 4. 第 2 阶段：ManiSkill 演示（建议 2–4 天）

**目标：**先看到推方块和抓方块，理解策略与仿真环境的接口。

- [ ] 参照 [ManiSkill 官方文档](https://maniskill.readthedocs.io/)安装，在固定版本中确认 `PushCube-v1`、`PickCube-v1` 的实际任务 ID 和可用控制模式。
- [ ] 先运行随机动作，再按该版本文档下载、回放官方示范或运行官方运动规划示例；记录数据来源、任务、控制器和渲染方式。随机动作不保证成功。
- [ ] 分别解释观测字段、动作维度与含义、奖励、成功判定和 episode 上限；保存一次成功演示及环境信息。
- [ ] 如果回放失败，核对机器人、控制模式、仿真后端、数据及环境版本；不要把回放失败归因于 PPO。

**阶段门槛：**可以重置场景并录制运动，能说明输入输出，至少成功回放一个适配版本的官方演示；若演示不可用，记录原因及替代视频，先进入低成本 PPO 冒烟测试。

## 5. 第 3 阶段：PPO 控制机械臂（建议 2–4 周）

**顺序：**先 PushCube，再 PickCube。两者都是状态观测优先，采用固定 ManiSkill 版本的[官方强化学习 baseline](https://maniskill.readthedocs.io/en/latest/user_guide/reinforcement_learning/baselines.html)，训练和评估命令以对应版本仓库 README 为准。

1. **冒烟测试。** 先少量并行环境、短时间运行：检查 reset、动作范围、奖励、日志、checkpoint 和评估视频。记录显存与每秒步数；小规模运行不代表已收敛。
2. **PushCube。** 固定控制模式与状态观测，运行 baseline。分别保存初始和训练后策略，按第 8 节评估并归类失败。
3. **PickCube。** 通过 PushCube 门槛后，在同一套记录规范下新建实验；先用官方默认奖励和任务设置。抓取通常更难，记录训练预算及失败，不承诺达到某个成功率。
4. **资源调整。** 显存不足时逐步减少并行数、batch 或视觉负担，记录变化；并行数改变可能影响 batch 构成和收敛，不能假设结果等价。先确认 checkpoint 可恢复，避免长时间盲跑。

**PushCube 门槛：**能加载本人训练的 checkpoint，至少 20 个独立评估回合有统计与视频；相对训练前或随机策略有可观察改善，或者诊断清楚并记录未改善的证据。未改善时先排查再进入 PickCube，避免把故障带入下一任务。

**PickCube 门槛：**完成训练与独立评估，保存成功/失败视频、配置、资源用量及失败分析；若预算内未抓取成功，也可作为已完成的失败实验，但须报告回合数和后续诊断，而非声称复现成功。

**建议产出：**`03_ppo_pushcube/`、`03_ppo_pickcube/`，各含配置、日志、模型、视频和 `report.md`。

## 6. 第 4 阶段：ACT 兼容仿真训练与评估（建议 2–4 周）

**默认项目：**[ACT 官方仓库](https://github.com/tonyzhaozh/act)的 `sim_transfer_cube_scripted`。该仓库提供脚本化示范采集、数据可视化、ACT 训练和同任务仿真评估；它使用双臂场景，与 ManiSkill PickCube 并非同一任务，也不要求先接通 LeRobot。

- [ ] 固定仓库 commit，按该版本 README 检查 Python、PyTorch、MuJoCo、`dm_control` 等依赖。原仓库给出较旧的环境；先单独验证与本机 GPU 的兼容性，若必须调整则逐项记录并做冒烟测试，不宣称原环境已复现。
- [ ] 按 README 生成或使用其提供的同任务示范，例如以 50 条完整 episode 为起点；记录生成种子、轨迹数量、成功质量和文件版本。可视化数条，确认图像、状态、动作与时间对齐。
- [ ] 先用少量数据和短训练验证读取、前向/反向、checkpoint 和评估启动；随后使用同版本官方训练配置作为基线。显存不足时优先减小 batch，并记录与官方配置的差异。
- [ ] 固定 checkpoint 选择规则；按照同版本官方评估入口在 Transfer Cube 中 rollout，保存成功和失败视频。确认脚本输出的成功定义及评估回合数；若脚本不支持所需的种子或回合数，增加薄封装并记录改动。
- [ ] 记录训练损失及验证损失，但以独立仿真任务成功率、失败类型和资源消耗评价闭环；loss 下降不等于任务成功。

**阶段门槛：**从同任务示范数据出发，完成本人训练、重新加载 checkpoint、独立仿真评估和视频；报告成功数/总数及失败原因。若只能加载数据或离线算 loss，明确标为“未完成仿真评估”，不进入正式消融。

**替代路径：**若旧 ACT 依赖无法与本机兼容，在独立环境尝试 [LeRobot 的仿真模仿学习教程](https://huggingface.co/docs/lerobot/main/il_sim)，完整采用其指定环境、采集方式、ACT 和评估流程；先核对该教程版本、控制设备需求和本机渲染。不可把任意公开数据直接用于不匹配的环境。ManiSkill → LeRobot 需另行验证转换、观测、动作、控制频率、归一化和 rollout；转换文件成功不等于策略可部署。

## 7. 第 5 阶段：示范数据量消融（建议 1–3 周）

**研究问题：**在同一任务和实验预算下，示范 episode 数量如何影响 ACT 的独立仿真成功率？

1. 从阶段 4 的合格示范中，先按完整 episode 划出固定验证集；训练候选池与验证集不重叠。留出独立评估初始条件，避免用测试结果选 checkpoint。
2. 若数据足够，以训练候选池的 **10 / 25 / 50 条**为示例；不够时如实改为可获得的 2–3 个数量，并确保最大组不含验证集。用固定种子抽样，保存 episode ID；可采用嵌套子集控制样本差异，并说明该设计的局限。
3. 保持模型、观测、动作、控制频率、优化器、batch、训练更新步数、checkpoint 选择规则和评估条件一致。固定更新步数意味着小数据组被重复采样更多；将此写成限制，必要时另做固定数据遍历次数的补充实验，不混为一谈。
4. 目标每组 **3 个训练种子**；资源不足先各 1 个作为试验性结果，报告不足并优先补种子。每个模型用相同的一组至少 50 个独立评估种子/回合，记录逐回合结果；计算各训练种子的成功率，报告均值及各次结果，而不是将所有回合当成独立训练重复。
5. 汇总数据量、训练种子、成功数/回合数、训练时间、峰值显存和典型失败。每个模型可附成功率的二项置信区间，解释其只反映有限评估回合的不确定性，不代替训练种子间变异。

**阶段门槛：**有预先写明的方案、数据划分与 episode 清单、可重跑配置、对照结果和 2–4 页“观察—证据—可能解释—局限—下一步”。若资源仅允许单种子，交付探索性结果并标明无法判断稳定性。

## 8. 随机种子与评估规范（各阶段通用）

- **训练与评估分离：**记录 Python、NumPy、PyTorch、环境、数据划分/采样所使用的种子；不同库和并行环境应显式设置并记录。固定种子不保证跨硬件、版本或 GPU 算子完全确定。
- **预先确定规则：**任务版本、初始条件分布、最大步数、成功判定、是否允许重复尝试、评估模式、checkpoint 选择和回合数。训练过程中用于调参的验证条件与最终测试条件区分。
- **同条件比较：**评估时关闭训练更新，保持观测、控制器、动作处理、归一化和控制频率一致；对照组尽可能使用相同的评估种子列表。
- **报告原始信息：**成功数/总回合数、成功率、各训练种子结果、失败类型、运行时长、硬件及版本。记录是否存在超时、异常或被排除的回合及原因，不能只展示成功视频。
- **最低与目标：**PPO 冒烟阶段至少 20 回合；正式消融目标每个模型至少 50 回合、3 个独立训练种子。预算不足时可以少做，但须标明为探索性结果及不确定性。

## 9. 进阶选修：Diffusion Policy / MuJoCo / SmolVLA

核心阶段完成后只选一个，避免同时开三条新线。

### 9.1 Diffusion Policy / Flow Matching

- [ ] 在可承担的任务上使用现成实现，或用低维状态/动作写简化实现理解噪声预测与动作序列采样。
- [ ] 仅在数据集、任务、观测、动作、控制频率及评估协议匹配时，与 ACT 对比成功率、推理延迟、训练成本和失败类型；如预算不同，明确说明。
- [ ] 8GB 显存可能限制图像训练；先测推理与短训练，不把能推理等同于能完整训练。参考 [LeRobot 策略文档](https://huggingface.co/docs/lerobot/)及对应版本依赖。

### 9.2 MuJoCo 独立实验

- [ ] 按 [MuJoCo 文档](https://mujoco.readthedocs.io/)加载机械臂 MJCF 和 viewer，执行关节位置或力矩指令。
- [ ] 先做末端到点，再考虑抓取；解释接触、碰撞、重力、仿真步长和控制频率。
- [ ] 产出可重复脚本、视频与参数说明。阶段 4 用到 MuJoCo 不代表已完成自定义任务。

### 9.3 SmolVLA

- [ ] 按 [SmolVLA 官方指南](https://huggingface.co/docs/lerobot/main/smolvla)先核对数据字段、相机映射和依赖；分别测推理与短时微调的显存。
- [ ] 如数据和资源足够，做同任务小规模微调及语言指令对照；冻结或参数高效训练仅在所选版本支持时采用。8GB 不保证可完成微调，失败时保留推理或资源评估报告。
- [ ] 不以本机从零训练大型 VLA 为目标。

## 10. 可并行项目：Robocon 深度相机视觉定位

利用已有 Orbbec、OpenCV 与视觉定位经验；每周安排少量固定时间，不阻塞主线。

- [ ] 描述 RGB 检测框 → 对齐深度 → 相机坐标 → 机器人坐标的转换链，记录内参、畸变、深度单位、坐标系和外参标定方法。
- [ ] 对比原始深度与 D2C 对齐深度的有效像素比例和缺失分布；分别记录分辨率、同步、深度范围与软件版本。
- [ ] 在不同距离、角度、材质、光照下重复测量；说明参考真值、误差定义、样本数与不确定性，报告均值/中位数及异常值，而不是只凭肉眼判断。
- [ ] 如有可用机械臂，完成下节适配后再测试抓取，记录尝试总数、成功判定与失败原因。

**产出：**一份标定流程、实验条件、误差表、示意图及改进建议组成的短报告。

## 11. 真实硬件适配与边界

- [ ] 先确认机器人型号、关节顺序、动作语义（位置/增量/速度/力矩）、单位、范围、夹爪方向、控制频率、相机视角和坐标系；与训练数据逐项对照。
- [ ] 检查相机内外参、手眼标定、时间同步、工作空间和障碍物；记录标定误差。核对归一化统计及图像处理与训练一致。
- [ ] 先离线回放和检查动作，再空载、低速、小范围逐步测试；设置限位、急停、人工监护及可中止条件。任何异常动作立即停止，排查后重新验证。
- [ ] 仿真与真机存在动力学、外观、延迟和接触差异；真机成功率应单独统计，不能沿用仿真结论。没有合适硬件时，此阶段保留为适配设计，不影响仿真主线验收。

## 12. 时间安排与弹性

| 时间段（仅供参考） | 核心任务 | 最小交付物 |
|---|---|---|
| 第 1 周 | 环境检查 + CartPole PPO | 环境记录、曲线、评估视频 |
| 第 2 周 | ManiSkill 演示 + PushCube 冒烟 | 演示视频、接口说明、短训练记录 |
| 第 3–5 周 | PushCube → PickCube PPO | checkpoint、评估统计、失败分析 |
| 第 6–9 周 | ACT 兼容仿真闭环 | 数据检查、训练日志、仿真 rollout |
| 第 10–12 周 | 数据量消融 | 对照表与导师汇报 |
| 后续 | 选一项进阶；Robocon 可并行 | 一个深入实验或视觉报告 |

每周按课程负担安排可用时间；依赖或算力受阻可延长，不将周次当作质量指标。紧张时优先保证阶段门槛、一次真实评估和记录，减少选修、参数搜索与视频数量；消融先做可负担的小规模探索，再补独立种子。

## 13. 易踩坑与失败退出机制

| 现象 | 先检查 | 限时后的退出或降级 |
|---|---|---|
| GPU 可见但运算报架构错误 | GPU 支持、驱动、PyTorch 构建与依赖 | 单独重建环境；仍失败则暂停重训练，先做 CPU 小样本接口验证，记录未完成 GPU 验收 |
| 黑屏或无法渲染 | 显示会话、Vulkan/渲染后端、GPU 驱动和无窗口设置 | 先用无窗口保存视频；仍失败则保留日志并处理 CartPole / 数据检查 |
| 显存不足或过慢 | 实测峰值、并行数、batch、图像尺寸、后台进程 | 减少资源占用并重测；记录改变及影响。仍无法训练则缩小实验或使用可获得的兼容算力，不把短跑当收敛 |
| PPO 奖励上升但任务不成功 | success 定义、评估模式、奖励分量、动作尺度和超时 | 对照随机/初始策略，保存失败；固定预算后转为失败报告，列最可能的下一项诊断 |
| ACT loss 下降但 rollout 失败 | 数据质量、时序、动作单位、归一化、checkpoint 和相机 | 先回放示范并核对单步接口；耗尽预算则停止消融，报告闭环未通过 |
| 安装依赖冲突 | 固定版本、Python 和二进制依赖，避免跨环境混装 | 每个阻塞问题先设例如半天排查上限；记录错误和尝试，改用上文兼容替代路径或暂停该阶段 |
| 数据或任务接口不匹配 | 机器人、控制器、频率、字段、坐标和成功判定 | 不直接训练/部署；先完成转换与回放验证，否则换同源数据和环境 |

**统一退出规则：**开始长实验前写下时间、显存和训练预算；先短跑。达到预算仍未通过时保存日志、配置、checkpoint、失败案例和下一步判断，向导师汇报后选择延长、降级或暂停。失败是可交付结果，但必须清楚区分“跑通接口”“完成评估”和“成功复现”。
